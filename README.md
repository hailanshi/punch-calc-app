# 打卡工资计算器 v2.1

单文件 `打卡工资计算器.html` 实现全部功能，无后端、纯本机存储；可直接双击用浏览器打开，
iPhone Safari 打开后「添加到主屏幕」即作为 PWA 使用；`ios-shell/` 内含极简 WKWebView 壳工程，
可交叉编译为 TrollStore 可安装的 IPA。

## v2.1 变更要点
- **新增「HR工资条对照 / 导入打卡」页**：登录公司 EHR（`hr.voopootech.net`）
  - **工资条对照**：只比工资条 —— 网页工资条的每一项 vs 本机算出来的同名项，逐项显示差额（本机 − 网页）。
  - **导入打卡**：把网页**原始打卡记录**导入本机打卡记录，按当天日期自动判定工作日/周末/法定节假日并拆分。

## HR工资条对照 / 导入打卡（v2.1）

「首页 → 📊 HR工资条对照 / 导入打卡」进入。点「读取HR数据」自动登录并取数，结果缓存在本机供离线对照。
页面只有三块：**网页工资条**（原始项）、**工资条对照**（vs 本机计算）、**网页打卡 → 导入本机**。
**不做考勤对照** —— 日考勤接口只用来标注「站点记为请假 N h」，不参与任何计算。

### ⚠ 两个接口的月份范围完全不同（关键）

| 数据 | 可查月份 | 实测 |
| --- | --- | --- |
| **工资条** | **任意月份** | 2026-07 ✅ / 2026-08 ✅ / 2026-09 未结算；≤2026-06 返回「只允许查询2026-07及之后月份」 |
| **考勤 / 原始打卡** | **只有本月 + 上月** | `month=0`=本月第 1 天；任何非 0 值（含 -1、-2、-6）都返回上月 |

所以：
- 查 7 / 8 月时**工资条照常显示**，只是没有打卡可导入 —— 界面会明确标注，不再把整个对照拦掉。
- 反过来 9 月（上月）有打卡、但工资条未结算，打卡导入仍然可用。
- **8 月永远无法做「工资条 ↔ 打卡」同月核对**：工资条能查，打卡取不到。

| --- | --- | --- |
| 登录 | `POST /LoginController.ashx` | 密码经站点 `Set_Secret` 混淆后提交 |
| 工资条 | `ctlGzsDetailRecordMobileMon.ashx?action=formatMulti&type_id=1&month=YYYY-MM` | 应出勤 / H1 / H2 / 应发 / 实发等；**对照的唯一依据** |

| 日考勤 | `ctlKqDetail.ashx?action=detail&month=N` | 仅取 `calc_field19/20/21…` 判断是否请假，在明细里标注，**不参与计算** |

### 打卡导入规则（公司班次口径）
工时**不按打卡分钟精确累加**，而是按公司班次口径折算，**统计一律取整数**：

| 项目 | 规则 |
| --- | --- |
| 正班 | 实际落在 `8:20-11:50` + `12:50-17:20` 内的时长，满勤 **8h** |
| 加班 | `18:00` 之后，正常 **3h** |
| 迟到 / 早退 | **如实扣减**（唯一需要计较分钟的场景） |
| 休息日上班 | 整天计入周末 / 法定加班档（约 **11h**） |

- 早到、17:20 之后的零星时间**不计**；「不计较那几分钟」正是指这个。
  例：真实打卡 `08:12 11:51 / 12:45 17:21 / 17:55 21:00` → **正班 8h + 加班 3h**（若按分钟精确累加会得到 11.33h，那是错的）。
- 实测 2026-09 全月 19 天导入：每条都是 `11h（8+3）`，总工时 **209h**，与公司口径
  （正班 136 + 平时加班 51 + 周休加班 22 = 209）**完全一致**。
- 导入的记录 `type='work'`、`note='HR导入 <打卡时间>'`，再用 App 自己的 `splitHours` 按日期判定拆分。
- 明细页每行**预演**导入后会计入哪一档（`→ 正班 8h + 平日加班 3h`），并显示 `11h（正班 8 + 加班 3）`。
- 已有记录的日期默认需二次确认才会覆盖；无打卡的日期（如事假、当天卡全空）不可导入，会跳过。
- **只有一条卡（漏打下班卡）不会丢弃整天**：末尾缺的那次按正常下班 21:00 补齐，
  明细里标红「⚠ 缺卡（只有 N 条，已按 21:00 下班补算）」，可自行取消勾选。
  完全没打卡的日期才跳过。
- **有多少天就导多少条**：只有 1 天打卡数据时导入 1 条，不会被当成"数据不足"拒绝。

### 月份对应（网页几月 ↔ 本机几月）
- **首页 / 记录页 / HR 页共用同一个月**，在任意一页切月，三处一起走，不会出现
  「记录页在 10 月、HR 页在 9 月」这种错位。
- **导入后自动切到数据实际所属的月份**，导入完直接就能在记录页看到，不用自己找。
- **查更早月份时不再强推月份**：工资条任意月份都能查，所以 App 会停在你选的月份。
  只有「工资条也没取到、且服务端把考勤回落到别的月份」时才对月份做一次对齐提示。
- 工资条对照页顶部显示对应关系：本机记录月 ｜ 网页打卡 ｜ 工资条。
- **跨月时直接拦掉金额差额**（不给无意义数字）：工资条月份（或打卡月份）≠ 查看月份时，
  对照区只列工资条原始项 + 三个月份，并提示「把 HR 页切到 X 月再读取」，不做任何相减。
  原因：8 月和 9 月的正班合计 / H1 / H2 / 底薪是**两套完全不同的数字**
  （8 月：168h / H1 60h / H2 22h；9 月：136h / 平时 51h / 周休 22h），直接相减必然得出错误结论。
  同月时才恢复正常逐项对照。
- 导入的打卡记录**直接参与 App 的工资计算**（calcMonth 读的就是这些记录）。
- **导入后没记录的工作日自动算缺勤**（calcMonth 原有逻辑：无记录 + 非休息日 → 缺勤），
  缺勤会清零全勤奖。反复导入覆盖不会累积也不会丢失：实测连续导入 4 次，
  始终 19 条记录 / 4 天缺勤 / 全勤奖 0，结果稳定。
- 导入前会**预览**本月有哪些工作日没记录、会算缺勤、会清零多少全勤奖，
  例如「⚠ 2026-09 有 4 天没有打卡记录（2、3、4、16 日），导入后这些天算缺勤，
  会清零全勤奖（¥100.00）」——这些天正是站点记为「事假」的日子。
### 已知口径与限制（重要）
- **考勤 / 打卡接口只有「本月 / 上月」两档**：`month=0` 是本月的第 1 天，任何非 0 值都返回上月，
  更早的月份取不到。跨月时页面会**红色告警**提示月份不一致。
- **日考勤字段只用于标注请假**（取自接口 `format_mobile` 的字段定义，勿臆测）：
  `calc_field19`=**事假_工时**、`calc_field20`=病假、`calc_field21`=年假 等。
  这些值**不参与工时或工资计算**，只在导入明细里显示「站点记为请假 N h（无打卡，不导入）」，
  提醒你这天在站点上算请假而不是出勤。App 不对照考勤汇总。
- **对照前建议先对齐参数**：工资条「基本工资」是当月底薪，本机底薪需按月锁定（设置页保存时写入当月）；
  「应出勤工时」可手动填到「本月标准工时」。未对齐时对照页会给出红色提示。
- **工时口径（H1/H2）只列出不比对**，因为公司统计方式（按整点）与 App（按实际分钟）不同。

## 功能速览
- 打卡页两种按钮：**上班打卡**（录入工时）/ **缺勤**（不填工时，直接记缺勤）；法定节假日休息、普通休息仍按日期自动判定
- **保存打卡后停留在打卡页**不回首页（日期保持在刚存的那天，方便接着录下一天）；从记录页点「编辑」进去的保存后回记录页
- 工时拆分：工作日 8h 内正常 + 超出平日加班；周末与「法定假期内的非当天休息日」全计周末加班；**仅法定节假日当天**计节假日加班
- 加班费两套算法**二选一、互斥**（`otMode`），全站只走 `otRatesFor()` 一个入口：
  - **固定时薪**（默认）：单价直接填（平日 23.28 / 周末 31.03 / 法定 46.55 元/小时），不随底薪变
  - **底薪倍数**：单价 = 底薪 ÷ 加班时薪分母 × 倍数（1.5 / 2 / 3），跟着底薪浮动
  - 两套参数都保存，设置页可即时切换；未生效那组灰显并标注「未参与计算」，**永远不会同时参与计算**
- 自动补卡：「补卡到今天 / 本月全部补卡」，跳过周末、法定节假日、已有记录，无确认弹窗直接执行，
  完成弹 toast（成功 X / 跳过 X / 失败 X）并回首页刷新
- 工资：底薪/岗位补贴/绩效按 出勤比例（有效工时÷标准工时,封顶 1）折算；全勤受缺勤清零；
  餐补=min(上班天数×15,360)；社保固定扣
- 设置：底薪/两套加班参数/社保/全勤/绩效/岗位/餐补/自动工时全可改，分五组折叠，一次只展开一组
- **每月标准工时两套方案**：手动填（工资条「应出勤工时」）或「联网更新」=工作日×8（接口 `/api/v1/misc/holiday-calendar`，调休已算）；两套写同一个值，以最后一次写入为准，可一键「清除本月」回到自动推算
- 记录：按月浏览、编辑、删除单条、删除全部；导出文本；导入支持「追加 / 覆盖」
- 法定节假日：内置法定**当天**清单（节假日加班档）与放假区间（区间内非当天走周末加班档）；2024–2026 为国务院实际安排，2027–2029 按修订后 13 天/年口径推算
- 自定义节假日可指定档位：**周末加班档**（第 2 档）或**节假日加班档**（第 3 档），列表里可一键「切档」
- **改动节假日会重算已有记录**：记录的 `n/d/w/h` 是打卡当时的归类快照，所以新增 / 删除自定义节假日或切档之后，
  `resplitRecords()` 会按新归类重新拆分全部记录并刷新工资（boot 时也跑一次，保证升级后历史数据算得对）
- 5 套主题、安全区适配、公告跑马灯（QQ 昵称+签名，失败显示欢迎语）

## 数据与隐私
所有数据存本机 `localStorage`（壳内同样持久化）。换机迁移：设置无需迁移，记录用「导出/导入」。

## 已规避的 iOS/WKWebView 坑（开发时已落实）
1. 不使用 JS 动态 `.onclick`；所有点击都是 HTML 内联 `onclick="window.全局函数()"`，函数显式挂到 `window`。
2. 弹窗确认不用闭包回调：先存 `{动作函数名, 参数}` 到全局，底部「确定」统一走 `doConfirmOK` 执行。
3. 弹窗/长列表：标题固定、内容独立滚动、取消/确定固定底部；无 `inset`；全站安全区适配（刘海+底部横条）。
4. 补卡无确认弹窗，直接执行 + toast；所有写操作均有 toast 反馈；关键业务外层 try/catch，单条出错不崩整体。

## 已知口径（按你的规则执行）
- **只有法定节假日「当天」上班走节假日加班档**；法定假期内其余休息日（含落在周末的日子）走周末加班档，与周末同档。
  当天清单见 `HOLI_3X`，依据《全国年节及纪念日放假办法》(2025-01-01 起 13 天/年) 与人社部 300%/200% 口径。
- **加班费两套算法互斥**，由 `otMode` 决定，只有一套参与计算（这是硬约束）：
  - `otMode:'rate'`（默认）：`加班费 = 工时 × otRate1/2/3`，单价写死不随底薪变
    （默认 23.28 / 31.03 / 46.55 = `2700 ÷ 174 × 1.5 / 2 / 3` 四舍五入到分，即工资条加班单价）
  - `otMode:'mult'`：`加班费 = 工时 × (底薪 ÷ stdOt) × ot1/2/3`，单价跟着底薪浮动
  - 两条路径都只在 `otRatesFor(ym, S)` 里分支一次，其余代码（calcMonth / 首页 / 打卡预览 /
    节假日档位 / 设置提示）一律用它的返回值，所以不存在两套叠加的可能
  - `stdOt`（加班时薪分母，默认 174）在 mult 模式下参与换算；在 rate 模式下只用于显示参考值「正常时薪 = 底薪 ÷ 174」
- 自定义节假日带 `kind` 字段决定档位：`weekend`=周末加班档（进 `w` 桶）、`holiday`/缺省=节假日加班档（进 `h` 桶）。
  旧数据没有 `kind` 时按节假日加班档处理，行为与改动前一致。
- **节假日改动 → `resplitRecords()` 重算全部记录**：`calcMonth` 读的是记录里的 `n/d/w/h`
  （打卡当时的快照），不重算的话新增节假日工资不会变。所以 addHoliday / delCustomHoliday /
  toggleCustomKind 之后都会重拆分全部记录，toast 里报告重算条数；`boot()` 也跑一次，
  保证老版本留下的数据按当前规则对齐。工时缺失但有拆分值的旧记录会被保留、不被清零。
- 缺勤：打卡页「缺勤」按钮走 `type='absent'`，`hours=0`。工作日没打卡本来就会自动算缺勤，按钮的价值在于
  **休息日/节假日也能显式记缺勤**（例如旷工）；任何缺勤都会清零当月全勤奖。
- 周末调休补班日识别为工作日（8h 内正常、超出平日加班）。
- 版本号集中在 `APP_VER` 常量；iOS 侧 `Info.plist` / `PunchCalc-Info.plist` 的
  `CFBundleShortVersionString` / `CFBundleVersion` 需同步（打 ipa 时以后者为准）。
- 金额与工时均四舍五入保留 **2 位小数**（各档加班、加班合计、总收入都先取整再相加，避免长小数累积误差）。
- 底薪默认 2700 元，且**按月保存**：设置里保存时写入「当前查看的月份」，某月没单独存过就跟随全局值。
  调薪时切到新月份再保存即可，历史月份不会被改写（例：8 月存 2520、9 月起存 2700）。
- **每月标准工时**同时就是底薪折算分母（`出勤比例 = min(有效出勤 ÷ 本月标准工时, 1)`），取值优先级：
  本月设过的值（`manual` 手动 / `net` 联网）→ 当月工作日×8 自动推算 → 设置里的兜底 `std`。
  存储格式 `{YYYY-MM: {h, src, at}}`；旧版本存的纯数字按手动值兼容读取。
- 2027 起官方调休通知尚未发布，放假区间与当天清单为推算值，官方发布后用「联网更新」/手工校正。

| `打卡工资计算器.html` | 浏览器 / PWA 直接打开 |
| `ios-shell/PunchCalcApp/Resources/index.html` | CI 打包 ipa 时注入到 App 里的那一份 |

改动后两份都要更新（CI 只读 `Resources/index.html`）：

```bash
cp 打卡工资计算器.html ios-shell/PunchCalcApp/Resources/index.html
cd ios-shell/PunchCalcApp && ./build-ipa.sh
```

> 建议改完用 `SHA256` 或 `git hash-object` 核对两份一致，避免又出现「两代版本」。

## 日常维护速查

改完东西按这个顺序走，别跳步：

```bash
# 1) 改业务文件（只改根目录那份）
#    打卡工资计算器.html

# 2) 跑自检：语法 / 内联 handler 与 window 导出一致性 / $('id') 与 HTML id 对齐 /
#    两套加班参数互斥 / 归类·工时·加班费·缺勤·节假日重算·标准工时两套方案 等 140+ 项
node tools/selfcheck.js 打卡工资计算器.html
#    → 必须「0 失败」再往下走；退出码非 0 就是有问题

# 3) 同步到 ipa 用的那一份，并核对哈希一致（CI 只读这份！）
cp 打卡工资计算器.html ios-shell/PunchCalcApp/Resources/index.html
git hash-object 打卡工资计算器.html ios-shell/PunchCalcApp/Resources/index.html   # 两个哈希必须相同

# 4) 提交并推送 —— 推 main 会自动触发云端打包
git add -A && git commit -m "..." && git push origin main

# 5) 等 Actions 跑完，下载 ipa
gh run list --repo hailanshi/punch-calc-app --limit 3
gh run download <run-id> --repo hailanshi/punch-calc-app --name punch-calculator-ipa --dir out
```

### 版本号要改三个地方

| 位置 | 字段 |
| --- | --- |
| `打卡工资计算器.html` | `var APP_VER = '2.0'`（设置页「⑤ 更多」与说明页显示） |
| `ios-shell/PunchCalcApp/Info.plist` | `CFBundleShortVersionString` / `CFBundleVersion` |
| `ios-shell/PunchCalcApp/PunchCalc-Info.plist` | 同上 |

> ⚠️ 本机（Windows）**没有 iOS 工具链**（无 xcodebuild / theos / clang），发不了 ipa。
> GitHub Actions 的 artifact 默认 **90 天过期**，要长期留存就把 ipa 发到 Release 里。

### 如果 `git push` 连不上 github.com

国内网络下 `github.com:443` 会间歇性不通，但 `api.github.com` 通常还是通的，可以这样区分：

```bash
git push origin main                                    # 失败：Failed to connect to github.com
gh api rate_limit --jq '.rate.remaining'                # 成功 → 说明只是 github.com 被挡
```

这时不必干等，可以用 Git Data API 把本地提交原样推上去（`tools/push-via-api.js`）：
它会读本地 HEAD 的原始 commit 对象（tree / parent / author / 时间 / 消息全部照抄），
逐个上传 blob 再建 tree 和 commit，**每一步都核对 SHA**，只有构造出的 commit 与本地
HEAD 完全一致时才更新分支引用 —— 不一致就直接中止，绝不产生分叉历史。
